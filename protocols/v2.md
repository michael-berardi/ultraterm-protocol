# UltraTerm Terminal Protocol v2

This document is the normative UTP v2 wire and reference-client specification. The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are interpreted as described in RFC 2119.

## 1. Transport

A UTP v2 server MUST listen on `~/.ultraterm/utp.sock`.

- `~/.ultraterm` MUST have mode `0700`; the socket MUST have mode `0600`.
- The server MUST accept same-user local connections only.
- The server MUST NOT expose UTP through TCP or another network listener.

A connection carries UTF-8 JSON Lines: one object request per line and exactly one object response per request, in order. A request MUST NOT exceed 65,536 bytes. Invalid, oversized, or unknown requests return `{"ok":false,"error":"DETAILS"}`. Unknown object fields MAY be ignored. Names are case-sensitive.

## 2. Session identity

Commands return sessions in this shape:

```json
{"id":"SESSION_UUID","slot":1,"title":"Terminal 1","pid":12345,"launchedOmp":true,"launchProfile":"PROFILE_NAME"}
```

`id` names one attached terminal. For a harness-backed terminal the server binds that ID to the durable terminal session, so the same ID survives an app restart and a slot renumber; a replaced, relaunched or closed terminal MUST NOT inherit an older ID, and a plain shell session receives a fresh ID on each attach. `slot` is the user-facing terminal assignment. Destructive plans bind to `id`, never to `slot` alone. Identity-bound operations and manager routes additionally bind to the native agent conversation behind the terminal, so an unchanged ID with a changed conversation is still rejected until it is registered again.

## 3. Commands

### 3.1 `list`

```json
{"cmd":"list"}
{"ok":true,"sessions":[{"id":"SESSION_UUID","slot":1,"title":"Terminal 1","pid":12345,"launchedOmp":true,"launchProfile":"PROFILE_NAME"}]}
```

`list` is read-only. `sessions` MUST contain every attached session. Clients MAY sort by `slot`.

### 3.2 `inspect`

```json
{"cmd":"inspect","slot":2,"lines":80,"raw":false}
{"ok":true,"id":"SESSION_UUID","text":"RECENT_OUTPUT"}
```

A request MUST select `id` or `slot`; `id` takes precedence. `lines` defaults to `80` and is capped at `1000`. `raw` defaults to false. The server reads at most the newest 65,536 bytes from a bounded PTY-output tail. This is output history, not reconstructed screen state; cursor redraws MAY appear as successive text.

### 3.3 `send`

```json
{"cmd":"send","slot":2,"text":"run the focused test","enter":true}
{"ok":true,"id":"SESSION_UUID","delivery":"pty-input-queued","ptyWritten":false,"agentAcknowledged":false}
```

A request MUST select `id` or `slot` and provide `text`. The server queues UTF-8 bytes to that PTY and appends carriage return when `enter` is omitted or true. `expectedId`, when present, MUST match the resolved target session ID; the server rejects a mismatch before queueing any bytes, so a slot that was replaced or renumbered is refused rather than typed into. A successful reply means the input was queued, not that an agent read or acted on it. `send` is command-capable and MUST be used only with explicit authority over that target terminal.

### 3.4 `message`

```json
{"cmd":"message","from":1,"to":2,"text":"Tests are green.","receiptId":"RECEIPT_UUID"}
{"ok":true,"id":"RECIPIENT_SESSION_UUID","receiptId":"RECEIPT_UUID","delivery":"durably-queued","recorded":false,"entryId":null,"acceptedByHost":false,"agentAcknowledged":false,"modelRead":false}
```

```json
{"cmd":"message","from":1,"to":2,"text":"Tests are green.","noticeOnly":true}
{"ok":true,"id":"RECIPIENT_SESSION_UUID","delivery":"workspace-notice-accepted","agentAcknowledged":false}
```

`from` and `to` MUST name live, distinct slots, and `text` MUST contain 1–4,000 Unicode characters after trimming. By default the server queues the text in the recipient's durable native conversation inbox: that form REQUIRES a client-generated `receiptId` UUID, MUST prove a live native conversation on both ends, and MUST fail rather than fall back to a PTY when the host is unsupported or expired. `noticeOnly:true` instead emits one ephemeral workspace banner and needs no receipt. `expectedId`, when present, MUST match the recipient session ID. Neither form enters a PTY, and v2 has no broadcast. `message.receipt` looks up the state of one `receiptId`.

**Receipt states.** Once the recipient host records a note (`recorded:true`, `entryId` set), the server traces it into the recipient's own native conversation:

- `modelRead:true` and `readAt` (epoch ms) when the recipient model first responded after the recorded entry: the note was in its context for that response.
- `agentAcknowledged:true` and `acknowledgedAt` when the recipient then produced output (text or a tool call).
- `deliveryState` is one of `durably-queued` · `queued-awaiting-host` · `unclaimed-host-unavailable` · `unclaimed-host-not-ready` · `claimed-awaiting-recording` · `recorded-awaiting-read` · `recorded-history-unavailable` · `recorded-entry-not-found` · `read` · `acknowledged`, and `guidance` states in plain language why a note is not yet read and what happens next (for example: the recipient is mid-step and takes queued notes into the model when the step ends). A client MUST NOT resend on any of these states.

A bounded wait adds `waitMs` (1–120000) and optional `waitUntil`: `recorded` (default), `read` or `acknowledged`. The reply carries `waitSupported`, `waitUntil`, `waitSatisfied` and `timedOut`; a timed-out wait returns the current state and never cancels, resends or retargets the message.

```jsonl
{"cmd":"message.receipt","receiptId":"RECEIPT_UUID","waitMs":30000,"waitUntil":"read"}
{"ok":true,"receiptId":"RECEIPT_UUID","recorded":true,"modelRead":true,"readAt":1790406005000,"agentAcknowledged":false,"acknowledgedAt":null,"deliveryState":"read","waitSupported":true,"waitUntil":"read","waitSatisfied":true,"timedOut":false}
```

### 3.5 `open`

```json
{"cmd":"open","profile":"PROFILE_NAME","title":"Worker","confirm":false}
{"ok":true,"confirmed":false,"would":{"slot":3,"profile":"PROFILE_NAME","title":"Worker"}}
```

```json
{"cmd":"open","profile":"PROFILE_NAME","title":"Worker","confirm":true}
{"ok":true,"confirmed":true,"session":{"id":"SESSION_UUID","slot":3,"title":"Worker","pid":12345,"launchedOmp":true,"launchProfile":"PROFILE_NAME"}}
```

`profile` is required; `title` is optional. `confirm` defaults to false. A dry run MUST NOT mutate state. The server chooses the lowest free permitted slot. A confirmed open assigns that slot; UltraTerm MUST attach the returned pane to the workspace.

### 3.6 `close`

```json
{"cmd":"close","slot":3,"confirm":false}
{"ok":true,"confirmed":false,"would":{"slot":3,"id":"SESSION_UUID"}}
```

```json
{"cmd":"close","slot":3,"expectedId":"SESSION_UUID","confirm":true}
{"ok":true,"confirmed":true,"closed":{"slot":3,"id":"SESSION_UUID"}}
```

A confirmed close MUST provide `expectedId` from a fresh dry run. The server MUST reject a missing or changed ID and revalidate `slot → id` under the mutation lock; pre-mutation failure leaves the slot untouched. Success gracefully closes the exact session and UltraTerm removes its slot and pane. If removal commits but a later cleanup step fails, the server returns `ok:false`, `committed:true`, and the `closed` identity while still emitting the closed lifecycle outcome; clients MUST NOT leave a stale pane.

### 3.7 `profile.switch`

```json
{"cmd":"profile.switch","slot":3,"profile":"QUALITY","confirm":false}
{"ok":true,"confirmed":false,"would":{"cmd":"profile.switch","slot":3,"profile":"QUALITY","id":"SESSION_UUID"}}
```

```json
{"cmd":"profile.switch","slot":3,"profile":"QUALITY","expectedId":"SESSION_UUID","confirm":true}
{"ok":true,"confirmed":true,"session":{"id":"NEW_SESSION_UUID","slot":3,"title":"Worker","pid":23456,"launchedOmp":true,"launchProfile":"QUALITY"}}
```

A confirmed switch MUST provide the dry-run ID and revalidate it after profile preflight. It replaces only that session while preserving slot, title, working directory, and dimensions. Startup failure SHOULD restore the previous session and MUST return `ok:false`. UltraTerm attaches the replacement before its startup health check, then repaints every live pane through the same appearance-refresh path used by theme changes. Successful, restored, and unrecoverable outcomes MUST remain distinguishable to the UI.

### 3.8 `register.manager`

```json
{"cmd":"register.manager","from":2,"fromId":"WORKER_SESSION_UUID","to":1,"expectedId":"MANAGER_SESSION_UUID"}
{"ok":true,"from":2,"managerSlot":1,"fromId":"WORKER_SESSION_UUID","managerId":"MANAGER_SESSION_UUID"}
```

`from` is the worker slot and `to` its manager slot; both MUST exist and differ. `fromId` (the worker's session ID) and `expectedId` (the manager's session ID) are REQUIRED, MUST be captured from `list`, and MUST NOT be inferred from a slot. The server MUST reject a missing or stale ID, MUST resolve both slots to a live native agent conversation, and MUST prove both conversations before it persists the route. Multiple workers MAY map to one manager; one worker has at most one current manager.

A route pins the worker and manager session identities together with their native agent conversations. It is not a slot mapping: after an app restart, a terminal replacement, or a slot renumber, a route whose pinned conversations no longer match MUST be rejected rather than redirected. Slot compaction and renames MUST NOT rewrite, migrate or drop routes, so a freed slot number can never adopt an older completion route.

The server's local route state is versioned separately from the wire: `~/.ultraterm/manager-map.json` is format version 3 while the wire version remains 2. Legacy slot-only records MUST NOT be read as identity routes, and a route file the server cannot validate is treated as empty rather than migrated.

### 3.9 `task.done`

```json
{"cmd":"task.done","fromId":"WORKER_SESSION_UUID","text":"Regression suite passed.","receiptId":"RECEIPT_UUID"}
{"ok":true,"id":"MANAGER_SESSION_UUID","receiptId":"RECEIPT_UUID","delivery":"durably-queued","recorded":false,"entryId":null,"acceptedByHost":false,"agentAcknowledged":false,"modelRead":false}
```

`fromId` and a non-empty, single-line `text` of at most 4,000 characters are REQUIRED. The server MUST resolve the manager from the worker's registered route; an explicit `to` overrides the route but MUST then carry that manager's `expectedId`. A completion whose sender or manager is not registered MUST fail with an error explaining how to register the intended conversations.

Delivery goes only to the manager's native conversation inbox. The server MUST NOT type the summary into any PTY, and it MUST reject a completion when either pinned conversation has changed since registration. `receiptId` is a client-generated UUID used for receipt lookup and server-supported deduplication; its receipt reports read and acknowledged states exactly as for `message` receipts.

### 3.10 Profile registry

```json
{"cmd":"profiles.list"}
{"ok":true,"profiles":[{"name":"quality","active":false,"builtIn":false}]}
```

```json
{"cmd":"profiles.create","request":{"name":"quality","model":"provider/model","thinkingLevel":"high","titleModel":null,"routing":"upstream/primary,upstream/fallback"}}
{"ok":true,"profile":{"name":"quality","active":false,"builtIn":false}}
```

```json
{"cmd":"profiles.remove","name":"quality"}
{"ok":true,"name":"quality"}
```

Profile operations MUST stay inside the user profile root. Names and model settings MUST be validated. `routing`, when present, is a provider-neutral comma-separated ordered list of upstream model IDs. Creation MUST be atomic. Removal MUST reject active profiles and MUST NOT follow symlinks outside the profile root.

## 4. Local client output helpers

The reference client passes a successful `inspect` response through the bundled
`uc encode --readable --stats` command by default. `utp inspect --no-uc` MUST
print the server's `text` value unchanged. This transformation is client-side
only and MUST NOT change the wire request or response.

`utp savings [--rate DOLLARS_PER_MILLION]` invokes the bundled local
`uc telemetry` command and prints its day, 7-day, 30-day, and all-time summary.
It is not a wire command and MUST NOT send telemetry over a network.

## 5. Universal handoff client

`utp handoff` is a guarded reference-client composition over `open`, `profile.switch`, `register.manager`, `inspect`, and `send`; it is not an additional wire command.

A packet MUST be a current-user-owned, non-symlink regular file under `/tmp`, mode `0600`, containing 1–16,384 bytes. Because its resolved path is typed into the worker PTY, the path MUST NOT contain control characters (C0, DEL or C1). It SHOULD contain: Goal; Current state; Completed; Remaining todos; Decisions and constraints; Resources and artifacts; Next action. It MUST NOT contain credentials, secret values, unnecessary transcript history, or dropped user requirements.

```sh
utp handoff --slot WORKER --profile PROFILE --packet /tmp/handoff.md --manager-slot MANAGER
utp handoff --new-slot --profile PROFILE --packet /tmp/handoff.md --manager-slot MANAGER
```

Confirmation MUST require `--user-authorized`, representing explicit user permission for the exact orchestration. Every handoff requires a live, distinct manager. A confirmed handoff MUST run from that manager terminal or from an external non-UltraTerm shell. In-place confirmation also requires the `--expected-id` printed by a fresh dry run.

Before any packet is submitted, a confirmed handoff MUST wait until the receiving session produces stable output and MUST register exactly that worker session ID against the manager session ID read from `list`, so the route pins both native conversations. A new-slot handoff MUST NOT submit the packet unless that registration succeeded, and it MUST pin the submission to the captured worker session ID so a slot that changed identity is refused rather than typed into. When preparation fails — readiness timeout, registration failure, or cancellation — no packet can be in flight, so the client MUST close only the pane it just opened, bound to the session ID it opened, and report the original error. When the submission was attempted but its outcome is unconfirmed (timeout, disconnect, malformed reply), the packet MAY already be delivering: the client MUST NOT close that worker, and MUST report its session ID so the operator can inspect, adopt, or close it explicitly. A manager MAY control multiple workers by repeating the authorized flow. The client then submits only a short instruction that points at the packet; the instruction is the sole PTY input, and registrations and completions are never typed into a PTY.

An agent MAY suggest handoff or scale-out after a dry run reports free capacity and observed system memory is comfortable. It MUST NOT confirm an open, close, switch, or handoff based only on its own suggestion or inferred permission.

## 6. Universal report client

`utp report` is a guarded reference-client extension, not a wire command. It sends one structured JSON payload to a user-owned local hook:

```sh
utp report --route team:group-alias --project project-name \
  --new "A new capability is now available." \
  --changed "An existing experience is easier to use." \
  --fixed "A user-visible problem no longer occurs." \
  --user-authorized
```

`route` is a private local alias for Telegram, a bot, a group, or a generic inbox. The hook owns chat IDs, provider tokens, authentication, final project labels, and delivery. UTP MUST NOT contain or log those values. External delivery requires explicit user authorization or a standing permission and SHOULD happen once, without a duplicate browser or provider call.

The client invokes the executable at `~/.ultraterm/report-hook`, overridden by `UTP_REPORT_HOOK`, and writes the JSON payload to standard input. The hook path and containing directory MUST be current-user-owned. The directory MUST be private; the hook MUST be a regular executable file that is not group/world writable.

For the default `report` kind, the payload contains `route`, `project`, `kind`, and three user-facing item arrays: `new`, `changed`, and `fixed`. At least one item is REQUIRED. Each CLI flag MAY be repeated; each item MUST be a single line of 1–240 characters, where any Unicode line boundary (including U+2028) ends a line. A section accepts at most 12 unique items and a report accepts at most 24 items total. Technical workflow details, verification, deployment mechanics, commit identifiers (including bare abbreviated or full hashes), rollback instructions, and protected values (for example credential-shaped tokens and `password=` style assignments) MUST be rejected rather than delivered. The hook renders only non-empty sections under `What's new`, `What's changed`, and `Fixes`, using one bullet per item. Paragraph-style `summary`, `verification`, and `rollback` fields are forbidden for text reports.

For `kind` `file` or `image`, `--file` is REQUIRED and MUST resolve to a regular, non-empty file no larger than 45 MiB whose realpath is sent as `file`; `summary` is an OPTIONAL caption of at most 1024 characters. `new`, `changed`, and `fixed` are forbidden for file and image deliveries.

`utp redact` is a second guarded extension over the same hook. It sends one structured payload:

```json
{"op": "redact", "project": "project-name", "route": "team:group-alias", "message_ids": [3, 7], "reason": "cleanup"}
```

`message_ids` carries 1-20 explicit positive-integer IDs, deduplicated and sorted; `reason` is 1-300 characters. Redaction deletes only the bot's own prior messages, only by explicit message ID — never by content match or bulk range. The hook resolves the chat for the route, deletes each message independently so one failure does not abort the rest, and MUST write a fail-open audit entry for every call. External delivery and redaction require explicit user authorization or a standing permission.

## 7. Security

UTP is a same-user local command boundary. Implementations MUST NOT bind, proxy, or forward it over a network; weaken `0700`/`0600`; follow untrusted profile or packet symlinks; include credentials in protocol traffic, examples, logs, or fixtures; or mutate terminal state without confirmation and identity checks.

## 9. UTP 2.2.0 diagnostics and transport recovery

UTP release 2.2.0 retains wire version 2. `diagnose` is additive and read-only:

```json
{"cmd":"diagnose"}
{"ok":true,"protocolVersion":"2.2.0","wireVersion":2,"activeConnections":1,"connectionLimit":16}
```

The connection counts above are illustrative, not fixed limits. `activeConnections`
and `connectionLimit` MUST be nonnegative integer counts. Servers MAY include a
bounded object of aggregate health counters. Diagnostics MUST NOT contain terminal
contents, prompts, credentials, session details, or private paths. Older v2 servers
MAY reject the command as unknown. `utp diagnose` prints the response as JSON.

The reference client accepts at most 1 MiB before the response newline and applies
a 10-second exchange deadline. Responses MUST be JSON objects with boolean `ok`;
a successful `inspect` MUST contain string `text`. EOF before the newline is a
truncated reply, not success, even if the partial line parses as JSON.

Clients MUST NOT automatically retry after request bytes may have been sent.
Failure before sending means no request was sent; failure after sending begins
leaves mutation outcome unknown. A send failure can be partial. Timeout, disconnect,
or invalid reply does not prove the mutation failed. Reconcile using read-only
inventory, diagnostics or receipt lookup before any user-authorized follow-up.
Read-only requests MAY be retried manually. Receipt-based deduplication, where
supported, does not make other mutations safe to replay. A message receipt reports
durable inbox state for a `receiptId` only: it MUST NOT be presented as native host
acceptance, agent acknowledgment, or proof that a model read the message.
App lifecycle recovery MUST NOT trigger automatic terminal restart, socket deletion
or mutation replay; obtain a fresh inventory and fresh destructive dry runs after
recovery. Every connection is re-established after a restart, so clients MUST
rediscover live sessions before identity-bound operations; a stale route or dry-run
ID MUST NOT be reused as proof that the same terminal or native conversation is
still present.
